# Changelog

Internal log of notable changes and known issues for the poster session app. Not user-facing; for contributors working on this repo.

## Unreleased

### Added
- **Compact mobile header redesign**. At phone widths the header's three pieces (logo, title, "Fall 2026") were fighting for one line - the title could wrap, the date got orphaned, and the bar ate vertical space the full-screen map needs. Reworked the `@media (max-width: 767px)` `.header` block in `index.html` (the "compact, always-visible bar" from the mobile bottom-sheet PRD) to compact it rather than just shrink it further:
  - "Fall 2026" now stacks under the title (`display: block`) instead of sitting inline beside it, so it stops competing for width.
  - The title's `font-size` is now `clamp(20px, 6vw, 26px)` instead of a fixed size, so it scales fluidly and never wraps across the phone-width range - verified even at its *largest* clamp bound (simulated via an injected style override, since this dev environment's window resize didn't take effect for a real narrow-viewport test) it still fits alongside the logo and info button with room to spare, which bounds the smaller, real-world sizes too.
  - `--mobile-header-h` goes from 40px to 52px - stacking the subheading needs a bit more height than the old inline layout did, but this is still a "status strip," not a shrunk copy of desktop's header. Every dependent rule (`.map-container`'s top offset, `.table-container`'s height calcs) already reads this custom property rather than a hardcoded number, so they picked up the new value with no separate edits.
  - The stacked layout initially shipped with the logo and subheading too small to read outdoors (logo ~22px vs. a ~40px-tall text block beside it; subheading down at 0.7rem/~11px). Fixed: `.header-logo` is now `height: 44px` to match the full height of the stacked title+subheading, and `.header h1 .subheading` is `font-size: 14px` (the floor for outdoor legibility) with `font-weight: 600`, `opacity: 0.85`, and `letter-spacing: 0.02em` so it stays clearly secondary to the title without dropping below readable.
  - `env(safe-area-inset-top)` was already respected here from earlier notch work - no change needed.
  - The gradient is flatter on mobile only (`linear-gradient(180deg, #fdba1f, #f0ad16)` vs desktop's diagonal `135deg` shine) - a subtle shine reads noisier on a strip this short, and flat gold sits cleaner behind black text. Desktop's header is unchanged.
  - Also renamed the visible header title from "HMC Poster Session" to "Poster Session Map" (both breakpoints share this markup) - the HMC logo right next to it already carries that branding, and the shorter title leaves more headroom against the width constraint above. The browser tab `<title>` (already different text) was untouched.
- **Easel badge label fit**, per the "Easel Label Fit & Map/Table Parity" PRD. Long easel IDs ("CSEP-2", "CCSEHC-1") were clipping in the table badge and the tooltip badge - both guessed a font size purely from label *length* (three independent, near-identical bucket tables: the map's own `LayoutAPI.calculateFontSize()`, plus separate copies in `index.html`'s `createColorIcon()` and inside `assets/js/layout-api.js`'s tooltip code), rather than measuring the actual rendered width, and the table/tooltip's buckets were tuned more generously than the map's - same guessing, different clipping outcome. The table badge is now the map marker's *exact* circle+text, scaled down via SVG viewBox - not an independently-fitted approximation:
  - `createEaselMarkerElements(easelId, bgColor, textColor)` (`assets/js/layout-api.js`) builds the actual `<circle r="14">` + `<text>` DOM elements shared by every marker-creation call site (`createLoneMarkerElement`, and both sides of the two-sided `createPosterMountElement`) - consolidating three previously-duplicated copies into one. Font sizing is the map's original `calculateEaselFontSize()` bucket table (now a single shared function, promoted out of `LayoutAPI` since it never used instance state), unchanged from before.
  - `renderEaselBadgeHTML(easelId, { sizePx, ... })` wraps that same circle+text in a small standalone `<svg viewBox="-16 -16 32 32" width={sizePx} height={sizePx}>` for the table and tooltip - since it's the identical numbers in the identical local coordinate space, whatever fits on the map fits here too, just visually smaller; no separate fitting logic to keep in sync, and nothing restyled in CSS (`.easel-pill--table`'s and `.info-title .easel-pill`'s fixed-size CSS rules were removed as dead).
  - The map's own marker DOM/interactivity (hover-scale, `data-side` pairing, `computeMaxZoomForLabelSize`'s zoom-limit calculation) is unchanged in behavior - only *where* the circle/text creation code lives moved, not what it produces (verified live: circle `r`/`stroke-width`, `<text>` `font-size`/content/`fill` are byte-identical between a map marker and its table badge for `C-17`, `E-9`, and `CCSEHC-1`; hover still grows `r` 14→16 and resets correctly).
  - Superseded an earlier version of this fix (real-measurement `canvas.measureText()` fitting with its own badge-diameter-growth logic) after review showed it produced inconsistent badge sizes across table rows - deleted entirely in favor of this simpler, exact-parity approach.
- **Poster map tooltip containment**, per the "Poster Map Tooltip Containment" PRD. On mobile, tapping a marker near the top of the map used to open its tooltip *below* the marker - exactly where the bottom sheet lives - spilling over the search bar, chips, and list; the title/body fonts (1.8-2rem / 1.5-1.6rem) were also roughly 2x the size needed, the main driver of the oversized box. Replaces two byte-identical, viewport-only `positionInfoPanelSmart()` copies in `assets/js/layout-api.js` with a single safe-area-aware placement engine on `PosterSessionMap` (`assets/js/script.js`):
  - **Safe area**: `getTooltipSafeAreaRect()` derives the tooltip's bounds from `.map-container`'s own live rect, clipped on the bottom by the mobile bottom sheet's live top edge (desktop's side-panel `#tablePanel` never overlaps vertically, so it's unaffected) - both measured via `getBoundingClientRect()` every call, no new event wiring needed since the sheet already writes its transform synchronously every drag frame. Respects `env(safe-area-inset-left/right)` via two new `:root` custom properties JS can read.
  - **Placement**: centered above the marker (arrow down, 8px gap) first; shifts horizontally into bounds if needed; if it still doesn't fit vertically, three text-scale-down steps in order (18→16px title/15→14px body/padding, then 3-line title clamp, then 2-line mentor-line clamp - floors enforced simply by there being no step past the third); if it *still* doesn't fit, pans the map (250ms, reduced-motion jumps instead) so the marker sits at 85% of the safe area's height before re-placing; last resort caps height and scrolls the body, title pinned. Never placed below the marker. A single rAF loop re-runs this every frame while a tooltip is open (pan/pinch/sheet-drag), hides (not closes) it if the marker scrolls out of the safe area and re-shows it if the marker returns, and always re-derives from full size first so it scales back up once room returns.
  - **Accessibility**: `#infoPanel` gets `role="dialog"`, a dynamic `aria-label` (the poster title), and a new close (✕) button; Escape now closes it (extends the existing global Escape handler); focus moves to the panel only for a tap/keyboard activation, never a mouse hover (threaded via a new `moveFocus` option so hovering across markers on desktop doesn't steal keyboard focus).
  - **Edge case**: if the sheet is fully expanded and the safe area is under 120px tall, the tooltip doesn't show at all - dispatches `poster-tooltip-suppressed` for `index.html` to scroll the already-highlighted marker's table row into view instead.
  - Verified live via synthetic touch/click dispatch and a real row-click → animated-pan → tooltip-open flow: full containment at several deliberately-engineered marker positions (near the top, requiring 0/partial/full text scaling, and requiring auto-pan), swap-without-flicker between two open tooltips, sheet-too-short suppression, Escape/✕ dismissal, and hover-vs-tap focus behavior. As with the touch-input PRD, momentum/animation-timing-dependent behavior (the live rAF tracking loop, the auto-pan's animated tween) is unreliable to test directly in this backgrounded Chrome-automation environment (`requestAnimationFrame` is throttled/suspended there) - confirmed correct by forcing `prefers-reduced-motion` to bypass the animation and jump synchronously instead, which produced fully-contained results every time; flagged for a real-device check, same as that PRD's precedent.
  - Not in scope, per the PRD's own non-goals or disclosed simplifications: the 120ms position-easing between placement steps (all repositioning is instant, which trivially satisfies `prefers-reduced-motion` too), a bespoke "large text size" detection path (the generic fit-check already falls through to the scroll fallback for any reason content doesn't fit, including iOS Dynamic Type), and the building/poster-*area* info panel (`selectArea()`/`showAreaInfo()`, unaffected - `this.posterAreas` is currently empty, a dead code path). No permanent automated test script was added (no test framework exists in this repo, per the touch-input PRD's own precedent).
  - **Follow-up, same day**: the containment PRD's literal 18px/15px baseline read too small in practice on both desktop (which never had containment pressure to begin with - the side panel doesn't overlap the map) and mobile. Bumped the shared `.info-title`/`.info-description` baseline to 22px/17px; the `.tt-step1` floor (16px/14px, the accessibility minimum) is unchanged, so the existing scale-down/auto-pan/scroll engine still has real room to shrink into when a bigger tooltip doesn't fit - verified live that a tight-safe-area case still escalates through the same steps and lands fully contained.
- **Map touchscreen input rework, Phase 1 (core physics)**, per the "Map Touchscreen Input Behavior" PRD, Tight preset (recommended there for small/dense maps like this floor plan), on `feature/touch-input-rework`. Reworks `assets/js/script.js`'s gesture handling (`initializeEventListeners()` and several new class methods) to match the PRD's Idle→Pending→Panning/Pinching state model:
  - **Removed the >1:1 pan speed multipliers** (`getPanSpeedMultiplier()`'s `1.15` and the separate `TOUCH_PAN_MULTIPLIER` of `1.4`, both dead code now). These were layered on top of an earlier, correct fix (`renderScaleFactor`, the CSS-px-to-SVG-user-units conversion) as an attempt to fix "sluggish" panning, but actually pushed tracking past 1:1 - directly against the PRD's central rule that the point under the finger must stay under the finger. `renderScaleFactor` alone (divided by `currentZoom`) already produces exact 1:1 tracking; verified live via synthetic touch/mouse dispatch (a 5px screen move produces exactly `5 * baseWidth/renderedWidth` content px, at every zoom level tested).
  - **Touch/mouse slop**: a drag no longer starts on the first `touchmove`/`mousemove` - a new explicit `gestureState` (`'idle'|'pending'|'panning'`) holds in `'pending'` until the finger/cursor moves 12px (Tight preset) from its down-position, then commits to panning from the **current** position, not the down-position (no jump - the slop distance itself is discarded, not applied in one frame). Verified live: sub-slop movement produces zero pan; crossing slop produces zero pan on that same event, with the next event panning 1:1 from the new anchor.
  - **Pinch slop + always-pan-via-midpoint**: two fingers now always pan (via their midpoint, 1:1, same bounds-clamped path as single-finger pan) even before any pinch is recognized; zoom only engages once finger-distance changes by `max(6% of start distance, 10px)`, and once engaged stays engaged for the rest of the gesture even if distance drifts back toward the start value (gesture locking - verified live: a two-finger pan with unchanging distance never zooms, and a pinch that returns to its starting distance stays in zoom mode rather than reverting to pan-only).
  - **Pan bounds**: dragging/flinging can no longer push the map fully off-screen. A new `getPanBounds()`/`clampPanToBounds()` pair (in `panX`/`panY` terms, derived from the content bounding box already used for content-fit zoom) hard-clamps every live drag and momentum step so at least half the viewport stays covered by content (Tight preset: zero overscroll past this). Verified via direct extreme-input calls to `clampPanToBounds()`.
  - **Momentum rework**: velocity is now tracked in raw screen-space px/ms over a trimmed ~100ms sample window (mirroring `bottom-sheet.js`'s own velocity calc), replacing the old content-space EMA. A release below 500px/s (Tight preset fling threshold) stops dead with no glide; above it, velocity is capped at 2500px/s and decays exponentially with a 150ms time constant, stopping at 20px/s or immediately upon hitting a pan bound (no bounce). Respects `prefers-reduced-motion` (no momentum starts at all).
  - **Zoom-limit rubber-banding**: pinching or ctrl+wheeling past `minZoom`/`maxZoom` now overscales up to 5% with damped resistance instead of hard-stopping, then springs back to the true limit via the existing `animateZoomTo` engine once the gesture ends. Verified live: a wildly oversized pinch (20x the start distance) still caps at exactly limit × 1.05.
  - **New gesture: two-finger tap to zoom out** one step (anchored at the gesture's midpoint), when both fingers touch down and lift together within 250ms with <10px movement each and no pinch-slop crossed - matched by nearest-start-point rather than touch identifier. Verified live (both the positive case and that a genuine two-finger pan does not misfire it); the app's own ~10-15ms-apart synthetic events showed the duration check reading >1s due to this dev sandbox's background-tab timer throttling inflating `setTimeout` delays - confirmed as a test-harness artifact, not an app bug, by re-running with zero-delay (back-to-back) dispatches.
  - Long-press, double-tap-drag continuous zoom, rotation, 44px marker hit-target rework, palm/edge rejection, a CSS-transform rendering rewrite, and tightness as a user-facing setting are explicitly deferred, not silently dropped - candidates for a follow-up once this phase is validated on real devices. Momentum decay timing, rubber-band spring-back animation timing, and real finger-to-content drift under pinch were not independently verifiable in this dev environment (requestAnimationFrame is throttled/suspended in a backgrounded automation tab) - flagged for a real-device check.
- Re-added the HMC branding header on mobile, this time as a compact always-visible bar (`position:fixed`, small logo/type, subheading inline instead of stacked) rather than the full desktop-sized one Phase 1 removed entirely. Sits above the map and sheet (`z-index:60`) via a shared `--mobile-header-h` custom property that `.map-container`'s top offset and `.table-container`'s height formula both reference, so the map fits into - and the sheet's Full state stops right below - the actual header height rather than a hardcoded guess. The info button stays relocated into the sheet's search row rather than moving back into this bar, keeping it as narrow as possible.
- **Mobile bottom sheet (Phases 1–2 of the mobile map redesign), on `feature/mobile-bottom-sheet`.** Replaces the old stacked 50/50 map/table layout and its chevron expand/collapse toggle with a full-screen map and a draggable bottom sheet, matching the Apple/Google Maps pattern. Mobile-only (`≤768px`); desktop's existing side-by-side layout is unchanged.
  - New `assets/js/bottom-sheet.js` (vanilla, no jQuery): owns the sheet's three snap states (Collapsed/Half/Full, named rather than pixel-based so they survive resize/rotation), a touch-event drag state machine with fling detection, tap-the-handle-to-cycle, tap-the-map-to-collapse (a new `maptap` `CustomEvent` dispatched from `PosterSessionMap`'s existing touch tracking in `script.js`, excluding marker/mount taps via the same selector already used elsewhere in that file), a dim overlay that fades in as the sheet nears Full, and the "Fit all" pill (the existing reset button, restyled and repositioned - it already ran the fly-to animation, no new camera code needed for that part).
  - `index.html`'s `.header` is hidden entirely on mobile; the HMC logo/title move into `#infoPopover` (shown only there on mobile) and `#infoButtonToggle` relocates into the sheet's search row at runtime (moved, not duplicated, so its existing click handler keeps working).
  - `PosterSessionMap` (`assets/js/script.js`) gains `setViewportInsets()`/`getInsetUserUnits()`/`getBaseRenderScale()` and a generalized `calculatePanForCoordinates()`/`computeContentFitZoomAndPan()`: fitting/centering now target the visible area above the sheet instead of the full container, letterbox-aware (the SVG has no explicit `preserveAspectRatio`, so it defaults to `xMidYMid meet` and can genuinely letterbox against the full-screen mobile container). With zero insets (desktop, or before the sheet sets any) this reduces exactly to the prior behavior - verified bit-identical. Every existing caller (initial fit, Fit-all/reset, search/row-to-marker centering) gets inset-awareness for free, with no call-site changes.
  - Selecting a table row now drops the sheet to Half on mobile (a `poster-row-selected` event from `applyRowSelection` in `index.html`) so the marker it just centered isn't left hidden under a Full sheet.
  - The existing marker-detection selector (`[data-side]` / `.color-marker` / `[data-point-id]`), already used four times in `script.js`, is now also used to exclude marker taps from `maptap` and to exclude the new dim overlay from ever starting a map pan/pinch.
- **Mobile bottom sheet, Phase 3 (partial).** Focusing the search field now expands the sheet to Full (a `poster-search-focused` event, same pattern as the row-selection hook above) so the on-screen keyboard doesn't fight a half-open sheet. ### Fixed
- iOS Safari scrolls the whole document to bring a focused input "into view," even when it's already fully visible inside a `position:fixed` sheet - reported as the search field's row disappearing off the top of the screen (behind the collapsing address bar) the moment it was tapped, leaving just table rows and the keyboard. `overflow:hidden` on `html`/`body` doesn't stop this, since it's Safari's own focus-scroll behavior rather than a CSS overflow concern; pinning `body` with `position:fixed` (the previous attempt at this fix) turned out not to be sufficient by itself either - confirmed by the same report recurring after that shipped. Layered on three more targeted fixes: (1) the viewport meta tag gains `interactive-widget=resizes-content` (Safari 17.4+/iOS 17.4+, Chrome 108+ - the purpose-built fix for this exact class of bug), so the layout viewport - and this app's `100dvh`-based sheet sizing - actually shrinks when the keyboard opens instead of the keyboard just overlaying a viewport that doesn't know it's there; (2) a `visualViewport` `resize`/`scroll` listener in `bottom-sheet.js` forcibly snaps `window.scrollTo(0,0)` if Safari drifts it anyway, as a fallback for pre-17.4 versions; (3) the sheet's search-focus-to-Full transition is now instant rather than animated, removing a window where Safari's focus-scroll heuristic could act on the sheet's pre-animation (stale) geometry. Not independently verifiable in this environment (no real iOS Safari available) - the app's own focus-triggered logic was confirmed correct via a directly-dispatched `FocusEvent` (`element.focus()` itself doesn't reliably fire in this automation setup, since the tab lacks real page focus), but the Safari-specific scroll behavior itself could only be reasoned about, not reproduced.
- `#infoPanel` (the marker hover/click tooltip) was nested inside `.map-container`, which on mobile is `position:fixed` with its own (low) z-index - a stacking context that capped the panel's `z-index:100000` regardless of how high it was set, so it rendered underneath the bottom sheet whenever the two overlapped (reported: opening a poster's tooltip while the sheet was open left it covered). Same root cause, same fix as the info popover and category dropdown earlier this session: relocated `#infoPanel` to the end of `<body>`, a sibling of the sheet instead of a descendant of the map container. Verified via `elementFromPoint()` at a deliberately-overlapping position that the panel now renders on top of the sheet.
- Mobile's initial map zoom was hardcoded to a 2.5x floor (`fitToContent()` in `assets/js/script.js`) to compensate for the old 40vh-tall mobile map panel, where a pure content-fit zoom looked too small. That panel no longer exists (mobile is full-screen now, per the bottom-sheet redesign), so the floor was just forcing an over-zoomed initial view with no compensating reason. Removed; the initial view now uses the same content-fit zoom as everywhere else.
- A CSS Grid gotcha in `#filter-form-container` (a grid item inside `#tablePanel`'s `display:grid`): its default `min-width:auto` let the new chip row's nowrap children force the row - and with it the whole fixed-position mobile sheet - wider than the viewport and off-center, instead of scrolling horizontally within its own bounds. Added `min-width: 0`.
- Bootstrap 3.3.7's own `@media (max-width:767px){.table-responsive{overflow-y:hidden}}` rule was silently winning the cascade over this file's own `.table-responsive{overflow-y:auto}` (equal specificity, and Bootstrap's `<link>` loads after this file's inline `<style>`, so it wins ties) - a real, previously-undiagnosed bug that's almost certainly why `ensureManualTouchScroll`/`initializeMobileTableScrollFix` (a hand-rolled touch-scroll-with-momentum workaround) existed at all. Fixed with a higher-specificity `#tablePanel .table-responsive` override; confirmed native scrolling works correctly (including the sheet's Full-state scrollTop-aware handoff back to the drag gesture), and removed the now-unnecessary and now-conflicting workaround entirely (`assets/js/script.js`).
- A CSS Grid gotcha in the same area: `.table-container`'s `1fr` row for the scrollable list was being overridden by the grid item's default `min-height:auto` (resolving to its content's intrinsic size), which would have made `overflow-y:auto` have nothing to scroll regardless of the fix above. Added `min-height:0`.

### Known Issues
- Mobile bottom-sheet Phase 3's remaining piece (card-style list rows on mobile) and Phases 4–5 (sheet detail view, `?easel=` deep links, desktop-panel confirmation pass) are intentionally not built yet - see `TODO.md`.
- Not verifiable from the local dev environment this was built in: real `env(safe-area-inset-*)` values against an actual notch/home-indicator, iOS Safari's dynamic toolbar show/hide interacting with `100dvh`, and real `backdrop-filter` rendering/performance. Needs a spot-check on a real iPhone.
- Category filter: a "Categories" dropdown next to the search bar, populated dynamically from the unique values in `poster-data.tsv`'s Poster Category column (comma-split, so a poster tagged `"Biology, Chemistry"` gets a checkbox for each). Selecting categories AND-combines with the text search to filter both the table and the map's marker visibility (`index.html`).
- "Clear search results" button: appears below the last table row whenever a search is active, as a larger/more discoverable redundant option alongside the small X already in the search bar. Clicking it clears the search and refocuses the input.
- Favicon using the existing HMC logo asset (`assets/HMC BGW RGB 150dpi.png`).
- "Loading map…" overlay shown while the map's initial zoom/pan is being computed, so the jump from the full zoomed-out canvas to the fitted default view happens off-screen instead of as a visible jerk on load. Has a triple-redundant reveal (fires on successful fit, unconditionally after the delayed marker-registration retry, and a hard 4s fallback) so it can never get stuck covering — and blocking clicks/taps on — the map.
- `PosterSessionMap.fitToContent()` (`assets/js/script.js`): computes the default view by fitting the actual rendered content (buildings + poster mounts, via `getBBox()`) instead of always showing the full nominal 1078x1558 canvas, which has large empty margins baked in. Without this, short/wide containers (the mobile map panel) letterboxed hard against the tall canvas and content rendered tiny. Also applies a higher minimum zoom floor on mobile viewports specifically, since even a tight content-fit still looks small in a `40vh`-tall panel.
- Table rows are now keyboard-operable (`tabindex="0" role="button" aria-label="View poster …"`, Enter/Space triggers the same marker-highlight as a click, visible focus ring) — previously the row-click-to-highlight-marker feature had no keyboard path at all.
- Subtle momentum/inertia on the mobile table's touch-scroll (`assets/js/script.js`, `ensureManualTouchScroll`): the table has a hand-rolled touch handler (needed so it can `stopPropagation`/`preventDefault` before the map's own pan/pinch handlers see the touch) that was doing raw 1:1 finger tracking with no native momentum, so it stopped dead the instant you lifted your finger. Now tracks smoothed velocity during the drag and coasts on release with an exponential decay, damped to ~55% of the raw flick speed so it stays gentle.
- **Google-Maps-style zoom easing, Phase 1** (per the zoom-easing PRD, `assets/js/script.js`): a shared animation engine (`runZoomAnimation`, log-space zoom interpolation + synchronized focal-anchored pan, one shared `cubicBezier()`-based easing curve set) now drives every discrete zoom path — the +/− buttons (×2/×0.5, eased, anchored at viewport center), mouse wheel notches and trackpad scroll (eased, anchored at cursor), reset (fly-to, shared fly-to curve), and search-result-to-marker centering (migrated off the old bespoke pan-only animation onto the same fly-to engine). `ctrl+wheel` (the trackpad pinch-to-zoom convention) does a live, unanimated, cursor-anchored zoom instead. `minZoom`/`maxZoom` are now computed at runtime instead of hardcoded (`minZoom` = fit-whole-map-in-viewport, `maxZoom` = the zoom at which a marker label reaches ~40px), recalculated after markers load, on debounced window resize/orientation change, and synchronously on fullscreen toggle (which resizes the map container without firing a `resize` event). `touch-action: none` added to `.svg-map` to tighten the "never let the browser pinch-zoom the page" guarantee alongside the existing JS `preventDefault()`/gesture-event handling. Pinch-zoom's existing focal-anchor math (which was already correct) was refactored into a shared `computeAnchoredPan()` used by both pinch and the new engine, rather than duplicated.

### Fixed
- `LayoutAPI.createSVGElement()` (`assets/js/layout-api.js`) was pulling every `path`/`rect`/`circle`/`polygon` in a loaded SVG via a blind `querySelectorAll`, including ones nested inside `<defs>`/`<clipPath>` — which are mask definitions, never meant to be drawn. In `strauss-plaza.svg`, two `<clipPath>` rects happened to sit exactly over the Parsons and Jacobs/Keck buildings; because they were last in document order they rendered as opaque white boxes on top, hiding both buildings entirely. Fixed by filtering out any matched element with a `defs`/`clipPath`/`mask`/`symbol` ancestor before cloning.
- A pre-existing missing closing `}` for the "Mobile optimizations" `@media (max-width: 768px)` block in `index.html` meant it never closed before the nested `@media (max-width: 480px)` block. Browsers were silently recovering from this at end-of-file, so nothing visibly broke, but it was fragile; added the missing brace while working in this area.

### Known Issues
- `tools/mount-editor.html` logs two console errors on load — `PosterSessionMap class not found - Layout API cannot initialize`. Cause: the page loads `assets/js/layout-api.js`, which tries to extend a global `PosterSessionMap` class, without also loading `assets/js/script.js`, which defines that class. Harmless for the mount editor (it doesn't use the Layout API extension — it has its own TSV load/export logic), but worth cleaning up or silencing.
